# Наблюдаемость {data-kicker="ГЛАВА 11 / ДЛЯ ИНЖЕНЕРОВ"}

::: lead
Руководитель поддержки пишет: «Анне так и не вернули деньги, агент сказал, что не смог. Почему?» В логах агента есть строка `refund failed`, и больше ничего. Был ли это сбой шлюза, ошибка в сумме, отказ песочницы или исчерпанный бюджет, из такой строки не понять. Чтобы отвечать на такие вопросы за минуту, каждый запуск агента должен оставлять трассу: дерево того, что он делал, сколько это заняло и чем кончилось.
:::

## Трасса и спаны

Трасса (trace) описывает один запуск агента целиком. Она состоит из спанов (span): у каждого есть имя, время начала и конца, статус, атрибуты и ссылка на родителя. Родительские ссылки складывают спаны в дерево. Эту модель используют стандарты распределённой трассировки, например OpenTelemetry [17], и её удобно брать для агентов без изменений.

В лаборатории трасса агента устроена так:

- `agent.run`: корневой спан; атрибуты: заявка, заказ, итоговое состояние;
- `llm.plan`: один шаг модели; номер шага, входные и выходные токены, выбранное действие;
- `tool.<имя>`: вызов инструмента; аргументы, число попыток;
- `attempt`: одна попытка вызова; номер, код ошибки;
- `approval.wait`: ожидание человека; сумма, ответ;
- `guard.veto`: охранное условие отклонило завершение; причина;
- `handoff`: передача задачи человеку; причина.

Время в трассировщике лаборатории задаёт вызывающий код, а не системные часы, поэтому одна и та же заявка всегда даёт одну и ту же трассу. Значит, трассы годятся для тестов: тест проверяет и итог, и путь к нему.

## Что логировать на каждом шаге

| Где | Что записать | Зачем |
|---|---|---|
| Шаг модели | номер шага, версия промпта и модели, токены, стоимость, выбранное действие | цена и воспроизводимость |
| Вызов инструмента | имя, аргументы, ключ идемпотентности, результат или код ошибки | что произошло в мире |
| Попытка | номер, пауза перед ней, код ошибки | диагностика повторов |
| Решение runtime | разрешено или правило отказа, фаза | безопасность и аудит |
| Переход автомата | откуда, событие, куда | где агент провёл время |
| Человек | кто, когда, что видел в карточке, что ответил | ответственность |

Две вещи стоит записывать особенно аккуратно. Ключ идемпотентности позволяет связать трассу агента с записью в платёжной системе. Версии промпта и модели позволяют понять, что поведение изменилось после выкладки, а не само по себе.

Чего не стоит записывать в открытом виде: персональные данные клиента сверх необходимого, номера карт, секреты. Письмо клиента в трассе лучше хранить по ссылке на тикет, а не копией.

## Поиск причины по трассе

Вернёмся к вопросу из лида. В лаборатории есть сценарий, где платёжный шлюз недоступен весь запуск. Трасса этого запуска содержит {{trace.outageSpans}} спанов, из них {{trace.outageErrors}} с ошибкой. Сокращённо дерево выглядит так:

```text
agent.run                    error  state=failed
  llm.plan                   ok     step=3 action=create_refund
  tool.create_refund         error  attempts=4
    attempt                  error  code=unavailable
    attempt                  error  code=unavailable
    ...
  llm.plan                   ok     step=6 action=give_up
```

Ошибок много, но почти все они пересказывают одну. Корневой спан помечен как ошибочный, потому что провалился вызов. Вызов помечен как ошибочный, потому что провалились попытки. Правило поиска первопричины в лаборатории простое: среди спанов с ошибкой взять те, у которых нет дочерних спанов с ошибкой, и из них самый ранний.

```ts
export function rootCause(spans: Span[]): Span | null {
  const errors = spans.filter((s) => s.status === 'error');
  const leaves = errors.filter((e) => !errors.some((c) => c.parentId === e.id));
  leaves.sort((a, b) => a.endMs - b.endMs);
  return leaves.length > 0 ? leaves[0] : null;
}
```

Для этой трассы ответ: `{{trace.causePath}}`, код `{{trace.causeCode}}`. Руководителю поддержки можно ответить одной фразой: платёжный шлюз был недоступен, агент сделал положенные повторы и остановился, деньги не списаны. Последнее утверждение тоже берётся из трассы: в ней нет ни одной успешной попытки `create_refund`.

::: {.note data-title="Коротко"}
Хорошая трасса отвечает на четыре вопроса без чтения кода: что агент пытался сделать, что из этого изменило мир, где он остановился и почему.
:::

## Метрики

Трассы отвечают на вопрос про одну заявку. Метрики отвечают на вопрос про все. Для агента минимальный набор такой:

| Метрика | Что показывает |
|---|---|
| Доля успешных задач | качество, с интервалом (глава 12) |
| Распределение числа шагов | застревания и длинные хвосты |
| Стоимость задачи, среднее и p95 | бюджет и аномалии |
| Время ответа p50, p95, p99 | что чувствует клиент |
| Доля передач человеку и их причины | где агент не справляется |
| Отказы песочницы по правилам | атаки и ошибки модели |
| Состояние circuit breaker | здоровье внешних сервисов |

Время ответа надо смотреть перцентилями, а не средним. Смоделируем {{trace.runs}} запусков агента, где у части запусков были долгие повторы.

| Статистика | Значение |
|---|---|
| Среднее | {{trace.mean}} |
| p50 (медиана) | {{trace.p50}} |
| p95 | {{trace.p95}} |
| p99 | {{trace.p99}} |

Среднее {{trace.mean}} выглядит неплохо и ненамного больше медианы {{trace.p50}}. Но каждый двадцатый клиент ждёт больше {{trace.p95}}. Именно эти клиенты пишут жалобы. Дин и Баррозо в статье «The Tail at Scale» [18] показали, почему в системах из многих вызовов хвост распределения важнее середины: чем больше вызовов в задаче, тем вероятнее, что хотя бы один попадёт в хвост.

В лаборатории перцентиль считается методом ближайшего ранга: p95 равен наименьшему значению, которого не превышают по крайней мере 95% выборки. Есть и другие определения с интерполяцией. На больших выборках разница мала, на маленьких её стоит указывать рядом с числом.

::: {.warn data-title="Типичная ошибка"}
Логируют только ответ модели и итог задачи. Когда агент ошибается, нельзя понять, ошиблась модель, инструмент, runtime или человек. Трасса без вызовов инструментов и решений runtime помогает только тому, кто хочет поругать модель.
:::

## Разбор инцидента по трассе

Когда приходит жалоба, разбор идёт в одном и том же порядке. Его стоит записать как инструкцию для дежурного.

::: {.flow data-title="Порядок разбора"}
1. **Найти трассу** по номеру заявки или заказа
2. **Итог** терминальное состояние и причина
3. **Мир** успешные записи и их ключи
4. **Первопричина** самый ранний ошибочный спан без ошибочных дочерних
5. **Сверка** ключи против записей во внешних системах
:::

Третий шаг самый важный для клиента: что уже изменилось в мире. Если в трассе есть успешный `create_refund`, деньги ушли, даже если агент потом упал. Пятый шаг закрывает случай неизвестного исхода: по ключу идемпотентности ищут операцию у провайдера и убеждаются, что трасса и платёжная система рассказывают одну историю.

## Сигналы тревоги

Метрики полезны, когда на них реагируют. Для агента поддержки разумный минимум сигналов:

| Сигнал | Порог для тревоги | Вероятная причина |
|---|---|---|
| доля успешных задач | падение заметно ниже обычного уровня | выкладка, сбой сервиса, новый тип заявок |
| два возврата с одной заявкой | любое появление | сломана идемпотентность |
| отказы песочницы | всплеск по одному правилу | атака или регрессия модели |
| circuit breaker открыт | дольше нескольких минут | авария внешнего сервиса |
| p95 стоимости задачи | рост после выкладки | агент стал делать больше шагов |

Сигнал о двойном возврате стоит в списке отдельно: он должен срабатывать на единичный случай. Его источник: простой запрос к данным провайдера: больше одного возврата на одну заявку.

## Что сделать на практике

1. Завести трассу на каждый запуск со спанами для шага модели, инструмента, попытки, ожидания и передачи.
2. Записывать ключ идемпотентности, версии промпта и модели, решения runtime.
3. Не хранить в трассах секреты и лишние персональные данные.
4. Автоматически находить первопричину: самый ранний спан с ошибкой без ошибочных потомков.
5. Смотреть время ответа и стоимость перцентилями, а не средним.

::: {.lab data-title="Лаборатория"}
`npm run demo:trace` печатает дерево спанов для запуска при недоступном шлюзе, первопричину и перцентили времени ответа. `test/trace.test.ts` проверяет метод ближайшего ранга, {{trace.p50}} и {{trace.p95}} на {{trace.runs}} запусках, путь к первопричине и число спанов в трассе.
:::
