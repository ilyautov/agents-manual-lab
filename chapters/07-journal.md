# Журнал и восстановление после падения {data-kicker="ГЛАВА 7 / ДЛЯ ИНЖЕНЕРОВ"}

::: lead
Анна заказала две подушки и одну хочет вернуть: возврат {{journal.amount}}. Агент создал возврат, и в эту секунду под ним перезапустили контейнер при обычной выкладке. Новый процесс поднялся, увидел незакрытую заявку и начал сначала. Анна получила два возврата по одной заявке. Агент, который работает дольше секунды, обязан переживать падение в любой точке, и проверять это нужно перебором, а не надеждой.

## Журнал событий

Состояние агента в памяти процесса исчезает при падении. Поэтому всё, что агент сделал, записывается в журнал (event log): упорядоченный список событий в базе, который переживает перезапуск. Каждая запись говорит, какой шаг завершён и с каким результатом.

Процесс восстановления, его называют replay (воспроизведение), читает журнал и восстанавливает картину: какие шаги сделаны, какие нет. Завершённые шаги пропускаются, их результаты берутся из журнала. Незавершённый шаг выполняется заново.

```ts
for (const step of STEPS) {
  if (done.has(step)) continue;
  point(`${step}:before_effect`);
  const key = useKeys ? `${JOB.ticketId}:${step}` : undefined;
  // ... выполнить шаг с ключом key ...
  point(`${step}:after_effect`);
  journal.push({ seq: journal.length + 1, step, result });
  point(`${step}:after_journal`);
}
```

У задачи {{journal.steps}} шагов: прочитать заказ, проверить политику, создать возврат, уведомить клиента, закрыть заявку. Функция `point` обозначает место, где процесс может упасть. Таких мест у каждого шага три.

## Опасная точка

Падение до эффекта безопасно: шаг повторится, будто его не было. Падение после записи в журнал тоже безопасно: при replay шаг будет пропущен. Опасна середина. Деньги уже ушли, а журнал об этом не знает. После перезапуска процесс выполнит шаг снова, как будто его не было.

Перенести запись в журнал до эффекта нельзя: тогда при падении между ними журнал скажет «сделано», а возврата не будет. Объединить эффект и запись в журнал одной транзакцией тоже нельзя: платёжный сервис живёт в другой системе. Этот зазор между двумя системами принципиален, его не закрыть порядком операций.

Закрывает его ключ идемпотентности из главы 3. При повторе шага runtime передаёт тот же ключ `T-5:create_refund`, и провайдер возвращает уже созданный возврат, не создавая новый. Ключ защищает от повтора того, что журнал не успел записать, а журнал избавляет от лишней работы: replay не вызывает сервис там, где результат уже известен. Подход сходится с тем, что описывает Клеппманн в главе об обработке потоков [12]: «ровно один раз» достигается не доставкой, а идемпотентной обработкой.

## Проверка перебором

Утверждение «агент переживает падение» проверяется только перебором. В лаборатории {{journal.points}} точек падения ({{journal.steps}} шагов по 3 точки). Тест запускает задачу с падением в каждой точке ({{journal.singles}} сценариев), а потом с каждой парой разных точек ({{journal.pairs}} пар): процесс упал, поднялся, на восстановлении упал снова в другой точке, поднялся ещё раз. Всего {{journal.scenarios}} сценариев.

| Вариант | Сценариев | Двойной возврат | Двойное письмо | Ровно один возврат и одно письмо |
|---|---|---|---|---|
| С ключами идемпотентности | {{journal.scenarios}} | {{journal.doubleRefundKeyed}} | {{journal.doubleMessageKeyed}} | {{journal.exactKeyed}} |
| Без ключей | {{journal.scenarios}} | {{journal.doubleRefundNaive}} | {{journal.doubleMessageNaive}} | |

Без ключей двойной возврат случается в каждом сценарии, где хотя бы одно падение пришлось на точку `create_refund:after_effect`. В каждом из них клиенту вернули {{journal.worstRefunded}} вместо {{journal.amount}}. Платёжный сервис ошибки не заметил. Его собственная проверка «нельзя вернуть больше стоимости заказа» не сработала, потому что две подушки стоят как раз два возврата. Защиты на стороне провайдера от бизнес-ошибки нет.

::: {.note data-title="Коротко"}
Ровно один эффект обеспечивает ключ идемпотентности, выведенный из заявки и действия: без него перебор падений находит дубли. Журнал во внешнем хранилище и replay нужны, чтобы после падения не повторять сделанную работу и знать, какие побочные эффекты уже случились (для отчёта о передаче, глава 5).
:::

## Что если сервис не поддерживает ключи

Не каждый внешний сервис принимает ключ идемпотентности. Тогда есть два пути. Первый: перед повтором спросить статус («есть ли возврат по заказу A-1005 на 3990 ₽ за последние 10 минут?»). Это работает, если у сервиса есть надёжный поиск по операциям. Второй: записать в журнал намерение до эффекта, а после падения в точке намерения не повторять автоматически, а передать заявку человеку на сверку. Медленно, зато без дублей.

Для длинных процессов из нескольких записей есть шаблон саги [11]: каждой записи сопоставлено компенсирующее действие (возврат отменяется встречной операцией), и при неудаче посредине процесс откатывает сделанное в обратном порядке. Для агента поддержки компенсация обычно хуже, чем идемпотентность: отменить письмо клиенту нельзя.

::: {.warn data-title="Типичная ошибка"}
Журнал ведут, но хранят его в памяти процесса или в локальном файле контейнера. При перезапуске он исчезает вместе с процессом, и replay начинает с нуля. Журнал агента живёт там же, где живут заказы: в базе, которая переживает выкладку.
:::

## Что хранить в записи журнала

Запись журнала должна позволять двум разным читателям сделать свою работу: процессу, который восстанавливается после падения, и человеку, который разбирает инцидент.

| Поле | Зачем |
|---|---|
| номер записи и время | порядок событий, без пропусков |
| заявка и шаг | что именно сделано |
| ключ идемпотентности | связь с записью у внешнего сервиса |
| аргументы и результат | восстановление состояния без повторного вызова |
| версия кода и промпта | понять, каким кодом сделан шаг |
| состояние автомата после шага | продолжить с того же места |

Журнал только дописывается, записи в нём не меняются и не удаляются. Исправление ошибки оформляется новой записью («возврат R-2 отменён, причина: дубль»), а не правкой старой. Тогда журнал остаётся доказательством того, что происходило.

## Восстановление новой версией кода

Между падением и восстановлением может пройти выкладка. Процесс, который продолжает задачу, уже работает с новым кодом, а журнал записан старым. Если новый код переименовал шаг или изменил порядок, replay может не узнать сделанный шаг и выполнить его снова.

Защита простая, но о ней нужно подумать заранее. Имена шагов в журнале стабильны и не меняются при рефакторинге. Если порядок шагов меняется, незавершённые задачи доводятся старой логикой или передаются человеку. Ключи идемпотентности строятся из бизнес-смысла (заявка и действие), а не из номера шага в коде, поэтому переживают и такие изменения.

Есть и обратный случай: задача ждёт человека неделю, за это время политика возврата изменилась. Продолжать её по старому решению или перепроверить? Правило стоит записать явно. Для денег безопаснее перепроверить политику перед записью, если с момента решения прошло больше заданного времени.

## Что сделать на практике

1. Записывать в журнал завершение каждого шага с результатом, в хранилище вне процесса.
2. При запуске восстанавливать состояние replay и пропускать завершённые шаги.
3. Для каждой записи использовать ключ идемпотентности из заявки и действия.
4. Перебрать в тестах падение в каждой точке и в каждой паре точек.
5. Для сервисов без ключей сверять статус или передавать человеку.
