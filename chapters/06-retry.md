# Ошибки и повторы {data-kicker="ГЛАВА 6 / ДЛЯ ИНЖЕНЕРОВ"}

::: lead
Агент отправил запрос на возврат 3990 ₽ и через десять секунд получил таймаут. Разработчик рассудил просто: ответа нет, значит возврата нет, повторим. Деньги ушли дважды: платёжный сервис успел провести первый возврат, а потерялся только ответ. Таймаут говорит о том, что мы не знаем исхода. Он не говорит, что действие не произошло.
:::

## Три класса ошибок

Прежде чем повторять, runtime классифицирует ошибку. Классов три, и у каждого своё правило.

| Класс | Примеры | Повторять |
|---|---|---|
| Временная (transient) | сервис недоступен, превышен лимит запросов, таймаут чтения | да, с паузой |
| Постоянная (permanent) | неверные аргументы, сумма больше заказа, нет прав | нет, вернуть модели |
| Неизвестный исход (unknown outcome) | таймаут записи, обрыв соединения после отправки | только с тем же ключом идемпотентности |

Третий класс самый коварный. Когда запрос на запись ушёл, а ответ не пришёл, возможны оба мира: сервис ничего не сделал или сделал и не успел сказать. Повторять вслепую нельзя. Не повторять тоже плохо: клиент останется без денег. Выхода два: повторить с тем же ключом идемпотентности, и тогда сервис сам разберётся, был ли первый запрос, или спросить у сервиса статус операции.

```ts
export function classify(code: string, isWrite: boolean): ErrorClass {
  if (code === 'timeout') return isWrite ? 'unknown_outcome' : 'transient';
  if (code === 'unavailable' || code === 'rate_limited') return 'transient';
  return 'permanent';
}
```

В лаборатории есть тот же сценарий, что в лиде: провайдер проводит возврат и отвечает таймаутом. После слепого повтора без ключа возвратов у провайдера {{retry.blindRefunds}}, после повтора с ключом `T-5:create_refund` их {{retry.keyedRefunds}}. Сквозной агент в таком же сценарии делает {{agent.timeoutAfter.toolCalls}} вызовов инструментов вместо {{agent.small.toolCalls}}, но возвратов у провайдера по-прежнему {{agent.timeoutAfter.refunds}}.

::: {.note data-title="Коротко"}
Таймаут записи переводит задачу в состояние «исход неизвестен». Из него два выхода: повтор с тем же ключом или запрос статуса операции у сервиса. Третьего нет.
:::

## Экспоненциальная пауза и jitter

Временную ошибку повторяют не сразу. Если сервис перегружен, мгновенный повтор только добавит нагрузки. Обычная схема: экспоненциальный backoff, пауза удваивается с каждой попыткой и упирается в потолок.

::: formula
::: f
пауза_i = min(cap, base · 2^i)
:::
При base = 200 мс и cap = 5000 мс шесть пауз равны {{retry.backoff}} мс, всего {{retry.backoffSum}}.
:::

У чистого backoff есть проблема, хорошо описанная в статье Марка Брукера из AWS [9]. Если сервис упал, все клиенты получили ошибку одновременно и повторят тоже одновременно: в моменты {{retry.moments}} мс после сбоя. Сервис, едва поднявшись, получает волну запросов и падает снова. Защиту от этого называют jitter (случайный разброс паузы). В варианте full jitter пауза выбирается случайно и равномерно в промежутке между нулём и экспоненциальной границей.

В лаборатории случайность детерминирована: генератор mulberry32 с фиксированным сидом (начальным значением генератора). С сидом 42 шесть пауз равны {{retry.jitter}} мс. Тот же сид всегда даёт те же паузы, поэтому тест может проверить их точно.

Чтобы увидеть эффект, смоделируем 1000 клиентов, которые получили ошибку в момент ноль и делают по пять повторов. Считаем, сколько запросов пришлось на самое загруженное окно в 10 мс.

| Схема | Пик запросов в окне 10 мс |
|---|---|
| backoff без jitter | {{retry.herdNoJitter}} |
| backoff с full jitter | {{retry.herdJitter}} |

Без jitter вся тысяча приходит в одно окно. С jitter пик падает больше чем в десять раз, а общее число повторов то же.

## Лимит попыток

Повторы ограничивают двумя числами: максимум попыток и потолок суммарного ожидания. В агенте лаборатории не больше четырёх попыток на вызов. После них ошибка возвращается модели, а дальше работает лимит перепланирований из главы 4. Без лимита попыток агент при долгой аварии будет вечно висеть в одном шаге, а бюджет времени тем временем расходуется: в лаборатории вызовы инструментов и паузы между попытками входят в него.

```ts
const canRetry = cls === 'transient' || (cls === 'unknown_outcome' && opts.hasKey);
if (!canRetry || attempt === opts.maxAttempts) {
  return { ok: false, attempts: attempt, waitedMs: waited, lastCode: code, errorClass: cls };
}
```

## Circuit breaker

Когда платёжный шлюз лежит минуту, каждая заявка всё равно делает свои повторы. Сто заявок дают сотни запросов к сервису, который заведомо не ответит. Шаблон circuit breaker (автоматический выключатель), описанный Майклом Найгардом в книге «Release It!» [10], останавливает это.

::: {.flow data-title="Состояния выключателя"}
1. **Замкнут (closed)** вызовы идут, неудачи считаются подряд
2. **Разомкнут (open)** после порога неудач вызовы сразу отклоняются
3. **Полуоткрыт (half-open)** после паузы идёт одна пробная попытка
4. **Итог** успех закрывает, неудача снова открывает
:::

Смоделируем аварию: шлюз лежит первые 60 секунд, запрос приходит раз в секунду в течение двух минут, каждый запрос делает до трёх попыток подряд. Выключатель открывается после пяти неудач подряд и ждёт 10 секунд.

| Вариант | Вызовов к лежащему сервису | Быстрых отказов | Обслужено после подъёма |
|---|---|---|---|
| Без выключателя | {{retry.deadNoBreaker}} | 0 | {{retry.servedNoBreaker}} |
| С выключателем | {{retry.deadBreaker}} | {{retry.fastFails}} | {{retry.servedBreaker}} |

С выключателем лежащий сервис получил {{retry.deadBreaker}} запросов вместо {{retry.deadNoBreaker}}. Цена: один запрос сразу после подъёма получил быстрый отказ, потому что выключатель ещё был открыт. Для агента быстрый отказ полезен: он сразу узнаёт, что сервис недоступен, и может передать задачу человеку, а не тратить шаги.

::: {.warn data-title="Типичная ошибка"}
Повторы настраивают на каждом уровне: SDK модели повторяет, HTTP-клиент повторяет, runtime повторяет, модель перепланирует. Если уровней {{retry.levels}} и на каждом по {{retry.perLevel}} попытки, число запросов на одну ошибку доходит до {{retry.nested}}. Решите, где живут повторы (обычно один уровень в runtime), и выключите их в остальных.
:::

## Какой таймаут выбрать

Таймаут сам по себе тоже решение. Слишком короткий превращает медленные, но успешные операции в «неизвестный исход» и плодит повторы. Слишком длинный держит агента и клиента в ожидании, пока сервис давно лежит. Разумный ориентир: чуть выше 99-го перцентиля времени ответа сервиса в нормальном режиме. Для записей таймаут обычно длиннее, чем для чтений: лишняя секунда ожидания дешевле, чем неизвестный исход и сверка.

У агента есть ещё один таймаут, о котором забывают: время ответа самой модели. Запрос к модели тоже может зависнуть или вернуть ошибку перегрузки. Здесь действуют те же правила: это временная ошибка, её повторяют с backoff, и это чтение с точки зрения мира, потому что вызов модели ничего не меняет. Повторять вызов модели безопасно, а вот выполнять дважды предложенное ею действие нельзя.

## Ошибки самой модели

Отдельный класс составляют ошибки формата: модель вернула вызов с неверным JSON, неизвестным инструментом или аргументами, не прошедшими схему. Это постоянные ошибки в смысле таблицы выше: тот же запрос даст похожий результат. Но их можно исправить, вернув модели понятное сообщение (глава 3). Обычно хватает одной-двух попыток. Если модель трижды подряд не может составить корректный вызов, проблема в описании инструмента или в задаче, и агенту пора остановиться.

## Что сделать на практике

1. Классифицировать каждую ошибку: временная, постоянная, неизвестный исход.
2. Повторять запись после таймаута только с тем же ключом или после запроса статуса.
3. Использовать экспоненциальный backoff с full jitter и детерминированным сидом в тестах.
4. Ограничить попытки и суммарное ожидание.
5. Поставить circuit breaker перед каждым внешним сервисом и показывать его состояние в метриках.
