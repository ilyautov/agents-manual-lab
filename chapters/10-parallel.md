# Параллельность и несколько агентов {data-kicker="ГЛАВА 10 / ДЛЯ ИНЖЕНЕРОВ"}

::: lead
Заявка Бориса проходит {{dag.tasks}} операций: прочитать заказ, клиента, политику и письмо, проверить на мошенничество, сверить с политикой, вернуть деньги, уведомить клиента, обновить CRM. Подряд это {{dag.sequential}} мс. Часть операций друг от друга не зависит, и их можно выполнять одновременно. Но как только параллельно работают две записи по одному заказу, появляется переплата. Параллельность у агента полезна для чтений и опасна для записей.
:::

## Граф зависимостей

Задачу удобно описать как DAG (directed acyclic graph, ориентированный граф без циклов): вершины означают операции, рёбра означают «эта операция ждёт ту». Чтения заказа, клиента, политики и письма ни от чего не зависят. Проверка на мошенничество ждёт заказ и клиента. Сверка с политикой ждёт заказ, политику и письмо. Возврат ждёт обе проверки. Письмо и CRM ждут возврат.

Если ресурсов хватает на все независимые операции сразу, каждая начинается, как только закончились её зависимости. Время задачи тогда равно длине самого долгого пути по графу. Этот путь называют критическим.

Ускорение всего в {{dag.speedup}} раза, меньше, чем хочется, и это типично. Самая долгая операция, проверка на мошенничество, стоит на критическом пути, и параллелить её не с чем. Ускорить задачу можно, только сократив операции на критическом пути. Сократить чтение политики бесполезно: у него и так есть запас.

## Параллельные вызовы инструментов

Многие API моделей позволяют за один шаг предложить несколько вызовов инструментов (parallel tool calls). Для агента это способ уменьшить число шагов: вместо четырёх шагов «прочитать заказ», «прочитать клиента», «прочитать политику», «прочитать письмо» один шаг с четырьмя вызовами. По арифметике главы 1 меньше шагов означает более высокую надёжность, а по главе 5 меньше токенов.

Runtime при этом должен соблюдать одно правило: параллельно выполняются только чтения. Если в одном шаге модель предложила и чтение, и запись, запись ждёт результатов чтений и проходит свою проверку отдельно. Два вызова записи в одном шаге выполняются последовательно, в порядке, который runtime может проверить.

## Как runtime исполняет пачку вызовов

Когда модель предложила несколько вызовов в одном шаге, runtime действует по правилам, которые не зависят от порядка, в котором модель их перечислила.

1. Каждый вызов проходит схему и песочницу отдельно. Отказ одного не отменяет остальных, но модель получает отказ в наблюдении.
2. Чтения запускаются одновременно, с общим таймаутом на пачку.
3. Записи ждут окончания чтений и выполняются по одной, каждая со своим ключом идемпотентности.
4. Если запись зависит от результата чтения из той же пачки, а чтение провалилось, запись не выполняется.
5. Модель получает результаты всех вызовов вместе, в том же порядке, в котором их предложила.

Четвёртое правило защищает от тонкой ошибки. Модель могла предложить «прочитать политику» и «создать возврат» одновременно, рассчитывая на то, что политика разрешит. Если чтение политики упало, runtime не должен исполнять возврат вслепую. В нашей песочнице это правило выражено проверкой `policy_not_checked`.

## Гонка за общий ресурс

Представим, что по заказу Бориса одновременно работают два экземпляра агента: один обрабатывает письмо про протекающий бак ({{dag.raceA}}), другой повторное письмо с просьбой вернуть {{dag.raceB}} за сломанный капучинатор. Остаток по заказу {{dag.raceRemaining}}. В худшем порядке оба экземпляра читают остаток раньше, чем кто-то из них запишет: оба видят {{dag.raceRemaining}}, оба проверяют «сумма меньше остатка» и оба создают возврат. Чтобы гонка была видна в чистом виде, провайдер в этом опыте остаток не проверяет: так бывает, когда остаток с учётом скидок и частичных отмен знает только магазин.

Лаборатория перебирает все {{dag.raceOrders}} порядков четырёх операций (два чтения и две записи, каждое чтение раньше своей записи) и выполняет их. Без контроля версии переплату дают {{dag.raceBadOrders}} из них, а именно все, где второе чтение случилось до первой записи. В таблице худший из них.

| Вариант | Вернули | Переплата | Конфликтов |
|---|---|---|---|
| Без контроля версии | {{dag.raceNaive}} | {{dag.raceOverpaid}} | 0 |
| С проверкой версии | {{dag.raceRefunded}} | 0 ₽ | {{dag.raceConflicts}} |

Проверка в каждом экземпляре была правильной, но на устаревших данных. Это классическое состояние гонки (race condition). Стандартное решение из мира баз данных называется оптимистичной блокировкой: запись проходит, только если версия заказа не изменилась с момента чтения. Второй экземпляр получает конфликт, перечитывает остаток ({{dag.raceReread}}), видит, что {{dag.raceB}} больше остатка, и отказывается. С проверкой версии переплаты нет ни в одном из {{dag.raceOrders}} порядков. Дальше заявка уходит человеку: две просьбы о возврате по одному заказу нужно согласовать.

Ключ идемпотентности здесь не помогает: у двух возвратов разный смысл и разные ключи. Нужен либо контроль версии, либо правило «одна заявка на заказ в работе одновременно», то есть блокировка на уровне заказа.

::: {.warn data-title="Типичная ошибка"}
Проверку «сумма не больше остатка» делают в инструменте до вызова платёжного сервиса и считают, что гонки нет. Проверка и запись разделены во времени, и между ними может пройти другая запись. Проверка должна быть частью записи (условие в той же транзакции) или защищена версией.
:::

## Много заявок одновременно

Гонка из предыдущего раздела возникает не только внутри одной задачи. Магазин обрабатывает сотни заявок, и агентов запущено много. Две заявки одного клиента по одному заказу («течёт бак» и «сломан капучинатор») легко попадают к разным экземплярам в одну минуту.

Самая простая защита работает на уровне очереди: заявки по одному заказу обрабатываются строго по одной. Очередь разбивается на разделы по номеру заказа, и в каждом разделе работает один исполнитель. Параллельность сохраняется между заказами, а внутри заказа гонок нет. Это дешевле и понятнее, чем ловить конфликты версий в каждом инструменте, хотя контроль версии всё равно стоит оставить как вторую линию.

Внешние сервисы тоже ограничивают параллельность. У платёжного шлюза есть лимит запросов в секунду, и сто агентов, одновременно создающих возвраты, получат ошибки `rate_limited`. Здесь помогают общий ограничитель скорости перед сервисом и повторы с jitter из главы 6, иначе агенты будут мешать друг другу.

## Когда нужно несколько агентов

Мультиагентная схема, в которой один агент планирует, второй исполняет, третий проверяет, выглядит привлекательно. Обзор Anthropic [3] советует начинать с простого и усложнять, только когда это окупается. Аргументы против лишних агентов следуют из предыдущих глав:

- каждый агент добавляет шаги, а шаги перемножают вероятности ошибок (глава 1);
- передача контекста между агентами теряет детали, и каждому нужно заново читать данные (глава 5);
- общие ресурсы порождают гонки, а их надо закрывать блокировками;
- трассу из нескольких агентов труднее читать (глава 11).

Несколько агентов оправданы, когда задачи действительно независимы (параллельный поиск по разным источникам), когда у частей разные права (агент, который читает почту, не должен уметь возвращать деньги) или когда нужна независимая проверка (второй агент без доступа к рассуждениям первого). Для возврата денег одного агента с хорошим runtime обычно достаточно.

## Что сделать на практике

1. Нарисовать граф зависимостей задачи и найти критический путь.
2. Ускорять операции на критическом пути, остальные не трогать.
3. Разрешить параллельные чтения, записи выполнять последовательно и проверять по одной.
4. Защитить общие ресурсы версией или блокировкой; проверку держать внутри записи.
5. Добавлять второго агента, только если есть одна из трёх причин: независимость, права, проверка.
