# Планирование и перепланирование {data-kicker="ГЛАВА 4 / ДЛЯ ВСЕХ"}

::: lead
Платёжный шлюз лёг на час. Агент попытался оформить возврат Анне, получил ошибку, подумал и решил попробовать ещё раз. Потом ещё. Каждый раз он добросовестно перепланировал: «шлюз недоступен, повторю попытку». Через полминуты агент упёрся в бюджет, потратив втрое больше обычного и не сделав ничего полезного. Перепланирование нужно агенту, но без лимита оно превращается в бесконечный цикл с хорошими намерениями.
:::

## План как данные

Агент может планировать двумя способами. В реактивном режиме модель на каждом шаге выбирает только следующее действие (так работает ReAct [1] и наш сценарный планировщик). В режиме «сначала план» модель выдаёт весь план целиком, а runtime исполняет его шаг за шагом. Оба режима полезны, и у второго есть важное свойство: план можно проверить до первого действия.

Для этого план должен быть данными, а не текстом. В лаборатории шаг плана описан так:

```ts
export interface PlanStep { id: string; tool: string; dependsOn: string[] }
```

Список таких шагов runtime проверяет по правилам: все инструменты существуют, зависимости ссылаются на более ранние шаги, длина плана не больше {{planning.maxSteps}}, а перед `create_refund` и `send_message` обязательно стоит `check_refund_policy`.

Хороший план возврата проходит проверку без ошибок. План, который модель составила после письма с инъекцией, не проходит проверку ещё до первого вызова. Ошибок {{planning.badErrors}}:

```text
s2: create_refund без предшествующего check_refund_policy
s3: нет инструмента export_customers
s4: зависит от s5, которого раньше нет
s4: send_message без предшествующего check_refund_policy
```

Проверка плана дешёвая: ни одного вызова сервиса, ни одного списания. Это самое раннее место, где можно поймать и ошибку модели, и попытку манипуляции.

## Проверка шага

План говорит, что делать. Проверка шага говорит, получилось ли. После каждого вызова runtime сравнивает результат с ожиданием этого шага. Для чтения ожидание простое: данные пришли и заказ тот самый. Для записи строже: возврат создан, сумма совпала, остаток по заказу уменьшился.

Если результат расходится с ожиданием, у агента три пути:

| Ситуация | Пример | Действие |
|---|---|---|
| Временная ошибка | шлюз ответил «недоступен» | повторить тот же шаг (глава 6) |
| План устарел | клиент уже получил частичный возврат | перепланировать от нового состояния |
| Цель недостижима | срок возврата истёк | закончить с понятным отказом |

Перепланирование уместно во втором случае. Мир изменился, и старый план больше не ведёт к цели. В первом случае новый план не нужен: шаг правильный, просто сервис временно не отвечает. Агент, который на каждую временную ошибку строит новый план, тратит шаги модели на то, что runtime сделал бы бесплатно.

Работа Reflexion [6] показала, что модель, которая записывает выводы из неудачной попытки и учитывает их в следующей, решает больше задач. Механизм полезный, но он работает на задачах, где повтор безопасен. Для возврата денег рефлексия без лимита означает ещё одну попытку списания.

## Лимит перепланирований

Вернёмся к лиду. Шлюз отвечает `unavailable` на каждый вызов. Runtime делает до четырёх попыток с паузами (глава 6), потом возвращает модели ошибку. Модель строит план заново и опять вызывает `create_refund`.

В лаборатории планировщик считает подряд идущие неудачи каждого инструмента. Если `create_refund` провалился больше {{planning.maxReplans}} раз подряд, планировщик сдаётся, и автомат переходит в `failed` с причиной.

| Вариант | Итог | Шагов модели | Вызовов инструментов | Стоимость |
|---|---|---|---|---|
| С лимитом перепланирований | {{agent.outage.state}} | {{agent.outage.steps}} | {{agent.outage.toolCalls}} | {{agent.outage.cost}} |
| Без лимита | {{agent.outageNoLimit.state}} | {{agent.outageNoLimit.steps}} | {{agent.outageNoLimit.toolCalls}} | {{agent.outageNoLimit.cost}} |
| Обычная заявка для сравнения | {{agent.small.state}} | {{agent.small.steps}} | {{agent.small.toolCalls}} | {{agent.small.cost}} |

Без лимита агента остановил только общий бюджет задачи (глава 5). Он закончил в `handed_off`, то есть тоже штатно, но потратил {{agent.outageNoLimit.cost}} на заявку, которую нельзя было решить; вызовов к лежащему сервису набралось {{agent.outageNoLimit.toolCalls}}. С лимитом агент понял это за {{agent.outage.steps}} шагов.

::: {.warn data-title="Типичная ошибка"}
Лимит ставят только на общее число шагов. Тогда агент, застрявший на одной ошибке, всегда тратит весь бюджет, а в трассах это выглядит как «агенту не хватило шагов, надо поднять лимит». Нужны два лимита: на задачу целиком и на повторение одной и той же неудачи.
:::

## Перепланирование после отказа runtime

Есть случай, когда перепланирование правильно и необходимо. В заявке Глеба письмо содержит инъекцию, планировщик один раз поддаётся и предлагает возврат 50 000 ₽. Runtime отказывает (глава 9), модель получает отказ runtime по правилу `amount_exceeds_order` и строит новый план от фактов: стоимость заказа 2490 ₽. Заявка решается за {{agent.injection.steps}} шагов вместо {{agent.small.steps}}. Отказ runtime не увеличивает счётчик неудач инструмента: это не сбой сервиса, а исправленная ошибка модели.

## Реактивно или планом

Выбор режима зависит от задачи, и его удобно делать по таблице.

| Признак задачи | Реактивный режим | Сначала план |
|---|---|---|
| Шаги известны заранее | избыточен | подходит |
| Следующий шаг зависит от результата прошлого | подходит | план часто устаревает |
| Есть необратимые записи | нужна проверка каждого шага | план проверяется до первой записи |
| Нужно показать человеку, что агент собирается сделать | неудобно | план и есть понятная карточка |
| Задача короткая, 3–5 шагов | подходит | лишняя сложность |

Для возврата денег хорошо работает смешанный вариант: шаги чтения агент выбирает реактивно, а перед первой записью формирует короткий план записей («вернуть 12 500 ₽, отправить письмо»), который runtime проверяет и при необходимости показывает человеку. План записей короткий, и его легко сверить с политикой.

## Ожидания шага

Чтобы проверка шага была кодом, а не впечатлением, ожидание записывают для каждого инструмента.

| Инструмент | Ожидание после вызова |
|---|---|
| `get_order` | заказ найден, клиент заказа совпадает с клиентом заявки |
| `check_refund_policy` | есть решение и сумма, сумма не больше стоимости заказа |
| `create_refund` | у провайдера есть возврат с этим ключом, остаток заказа уменьшился на сумму |
| `send_message` | письмо ушло на адрес клиента заявки, по заявке одно письмо |

Ожидание для `create_refund` проверяет состояние у провайдера, а не ответ инструмента. Ответ мог потеряться (глава 6), а состояние у провайдера останется правдой.

## Что модель видит после неудачи

Качество перепланирования зависит от того, что модель получает в ответ на неудачный шаг. Сравните два наблюдения после отказа runtime в заявке Глеба. Первое: «Ошибка». Второе: «Отказ runtime, правило amount_exceeds_order: к возврату доступно 2490 ₽, запрошено 50 000 ₽. Возврат не создан». Из первого модель не поймёт, что исправлять, и может повторить тот же вызов. Из второго следует очевидный новый план.

Хорошее наблюдение после неудачи содержит четыре части: что не получилось, почему (код и правило), что осталось неизменным в мире («возврат не создан») и, если runtime знает, допустимые значения. Последняя часть экономит шаги, но требует осторожности: подсказка «доступно 2490 ₽» уместна, а подсказка вида «чтобы обойти правило, сделайте так-то» превращает отказ в инструкцию для атакующего.

Для временных сбоев наблюдение другое: «платёжный шлюз недоступен, сделано 4 попытки, возврат не создан, повтор возможен позже». Здесь важна фраза о том, что runtime уже повторял. Без неё модель решит, что повторить стоит ей, и потратит ещё один шаг на то же самое. Именно это и происходит в сценарии без лимита перепланирований.

## Что сделать на практике

1. Если модель выдаёт план целиком, принимать его как структуру и проверять до исполнения.
2. Для каждого шага записать ожидание, которое runtime проверит после вызова.
3. Различать временную ошибку, устаревший план и недостижимую цель, реагировать по-разному.
4. Ограничить подряд идущие неудачи одного инструмента, а не только общее число шагов.
5. Сдаваться явно: состояние `failed` или `handed_off` с причиной, которую прочитает человек.
