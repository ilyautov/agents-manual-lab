# Инструменты как контракты {data-kicker="ГЛАВА 3 / ДЛЯ ИНЖЕНЕРОВ"}

::: lead
Модель предложила вызвать `create_refund` с аргументами `{"orderId": "A1004", "amount": -500, "card": "2200"}`. В номере заказа нет дефиса, сумма отрицательная, а поля `card` у инструмента вообще нет. Если такой вызов дойдёт до платёжного сервиса, в лучшем случае он вернёт непонятную ошибку, в худшем примет часть аргументов. Поэтому инструмент агента проектируют как публичный API: со схемой, проверкой до вызова и ответами, по которым модель может исправиться.
:::

## Контракт инструмента

У каждого инструмента в лаборатории есть описание: имя, вид (чтение или запись) и схема аргументов.

```ts
{
  name: 'create_refund', kind: 'write', args: {
    orderId: { type: 'string', required: true, pattern: '^A-\\d{4}$' },
    amount: { type: 'integer', required: true, min: 1, max: 1_000_000 },
  },
}
```

Похожие описания используют все крупные API с вызовом инструментов, обычно в формате JSON Schema. Протокол MCP (Model Context Protocol) [7] стандартизирует, как такие описания и вызовы передаются между приложением и сервером инструментов. Формат вторичен. Главное, что схема живёт в коде runtime и проверяется кодом; показать её модели недостаточно.

В нашем агенте {{tools.specs}} инструмента: {{tools.reads}} читают (`get_order`, `check_refund_policy`) и {{tools.writes}} пишут (`create_refund`, `send_message`). Это разделение влияет почти на всё в следующих главах: чтения можно повторять и запускать параллельно, записи нельзя.

## Валидация до вызова

Runtime проверяет аргументы до того, как вызов уйдёт в сервис. Для вызова из лида проверка находит ошибки, всего {{tools.badErrors}}:

```text
card: лишнее поле, допустимы orderId, amount
orderId: не подходит под формат ^A-\d{4}$, получено "A1004"
amount: ожидается от 1 до 1000000, получено -500
```

Посмотрите на форму ошибок. Каждая называет поле, ожидание и то, что пришло. Такой текст возвращается модели как результат вызова, и на следующем шаге она может исправить аргументы. Сообщение «400 Bad Request» модели не поможет: она не знает, что именно исправлять, и часто повторяет тот же вызов.

Лишние поля отклоняются, а не игнорируются. Если молча выбросить `card`, модель решит, что возврат ушёл на указанную карту, и напишет об этом клиенту. Отказ с объяснением надёжнее.

::: {.note data-title="Коротко"}
Схема ловит форму: тип, формат, диапазон. Смысл она не ловит: сумма 2490 ₽ допустима по схеме, но может быть больше остатка по заказу. Такие проверки делает сам инструмент или песочница (глава 9) и возвращает понятный код, например `amount_exceeds_order`.
:::

## Ключ идемпотентности

Первая книга разбирала идемпотентность webhook (уведомления, которое внешний сервис присылает приложению по HTTP): одно событие приходит дважды, а запись должна появиться один раз. У агента та же задача стоит острее. Вызов записи могут повторить runtime после таймаута, процесс после перезапуска или сама модель, которая «не увидела» ответ.

Решение то же: каждая запись несёт ключ идемпотентности. Сервис запоминает ключ и на повтор с тем же ключом возвращает прежний результат, не выполняя действие снова. Так устроены, например, idempotent requests в API Stripe [8]. В лаборатории ключ строится из заявки и действия, `T-1:create_refund`, и не зависит от попытки, процесса или формулировки модели.

```ts
if (spec.kind === 'write' && !key) return fail('missing_idempotency_key', 'запись без ключа идемпотентности запрещена', false);
```

После трёх вызовов `create_refund` с одним ключом число возвратов у платёжного провайдера равно {{tools.sameKeyRefunds}}, и все три ответа содержат один и тот же идентификатор `R-1`. Вызов без ключа runtime не выпускает вовсе, код ошибки `{{tools.noKeyCode}}`. Если тот же ключ придёт с другой суммой, сервис не вернёт молча старый результат: Stripe в таком случае отвечает ошибкой, и сервис лаборатории тоже, с кодом `{{tools.mismatchCode}}`. Иначе ошибка в сумме спряталась бы за ответом «всё в порядке».

Ключ нельзя генерировать случайно на каждый вызов: тогда повтор получит новый ключ, и защита исчезнет. Выбор ключа нельзя доверить модели: она может придумать новый. Ключ выводится из бизнес-смысла: «возврат по заявке T-1». Если по одной заявке законно нужны два возврата, у них разный смысл и разные ключи.

## Ошибки, понятные модели

Результат любого вызова в лаборатории имеет одну форму:

```ts
type ToolResult =
  | { ok: true; data: unknown }
  | { ok: false; error: { code: string; message: string; retryable: boolean } };
```

Поле `retryable` подсказывает runtime и модели, есть ли смысл повторять. Таймаут или недоступность сервиса повторяемы, неверные аргументы и `amount_exceeds_order` нет. Глава 6 разберёт, почему таймаут записи считается особым случаем.

| Код | Пример причины | Повторять | Что делать модели |
|---|---|---|---|
| invalid_arguments | сумма −500 | нет | исправить аргументы |
| amount_exceeds_order | 50 000 ₽ при заказе 2490 ₽ | нет | пересчитать сумму или остановиться |
| missing_idempotency_key | ошибка runtime | нет | ничего, это баг кода |
| idempotency_key_mismatch | тот же ключ, другая сумма | нет | ничего, это баг кода |
| unavailable | шлюз недоступен | да | ждать, runtime повторит сам |
| timeout | нет ответа 10 с | только с ключом | ждать решения runtime |

::: {.warn data-title="Типичная ошибка"}
Один инструмент `call_api(method, url, body)` вместо четырёх узких. Он удобен на старте и опасен потом: схема ничего не ограничивает, чтение не отличить от записи, права нельзя выдать на шаг. Узкий инструмент с бизнес-именем (`create_refund`) проверяется, логируется и разрешается отдельно.
:::

## Описание инструмента для модели

Схема проверяет вызов, а описание помогает модели выбрать правильный инструмент. Хорошее описание отвечает на три вопроса: что делает инструмент, когда его вызывать и когда нет. Для `create_refund` оно может звучать так: «Создаёт возврат денег на исходный способ оплаты. Вызывай только после `check_refund_policy` и только на сумму, которую она вернула. Не вызывай для обмена товара и для компенсации доставки».

Последняя фраза кажется лишней, но именно она снижает число ошибочных вызовов: модель склонна применять инструмент шире, чем задумано. При этом описание остаётся подсказкой, а не защитой. Правило «только после проверки политики» дублируется в песочнице (глава 9), и если модель его нарушит, вызов не пройдёт.

Имена аргументов тоже часть описания. `amount` без единиц провоцирует ошибку: рубли или копейки? Лучше `amount_rub` и целое число. Перечисления лучше свободных строк: `reason: "defect" | "not_fit" | "late_delivery"` проверяется схемой и даёт понятную аналитику.

## Версии контрактов

Инструменты меняются: появляется поле, меняется формат номера заказа. Модель при этом может продолжать вызывать старую форму, если она видела её в примерах промпта или в истории задачи, начатой до выкладки. Здесь помогают три правила:

1. Новые поля добавлять необязательными, с безопасным значением по умолчанию.
2. Старую форму принимать ещё какое-то время и логировать, кто её использует.
3. Записывать версию контракта в трассу каждого вызова, чтобы связывать ошибки с выкладками.

Ключ идемпотентности при смене версии не меняется: возврат по заявке T-1 остаётся тем же возвратом, какой бы формой его ни вызвали.

## Что сделать на практике

1. Для каждого инструмента записать схему, вид (чтение или запись) и смысловые проверки.
2. Запретить лишние поля и возвращать ошибки с полем, ожиданием и фактом.
3. Требовать ключ идемпотентности на каждой записи и выводить его из заявки и действия.
4. Отмечать в ответе, повторяема ли ошибка.
5. Не давать модели универсальных инструментов вроде произвольного HTTP или SQL.
